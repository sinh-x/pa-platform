## Must-fix findings

### R1 — Critical: retained uncertain custody does not fence v2 effects

**Evidence:** `packages/pa-core/src/documents/handoff-publication.ts:156–162` replaces v2 availability admission with `assertEffectCaller`, but that function (`handoff-preflight.ts:129–146`) checks caller/history/workflow, not prepared-ticket custody. Branch completion uses `RegistryHandoffGitOwner` directly, bypassing the same-ticket reservation check at `handoff-preflight.ts:53–61`. The underlying exclusion at `packages/pa-core/src/deploy/ticket-concurrency.ts:489–494` accepts every parsed prepared reservation without checking its occupancy/custody; it does not guarantee that an unrelated preparation is idle.

**Reproduced:** After valid approval/publication, created a real reservation through `withPreparedTicketCapacity`, then transitioned it to `occupancy: uncertain-retained`, `custody.state: uncertain-blocked`. Both the origin caller and a genuinely authenticated fresh selected continuation completed physical ref/link and queue with `ok:true`. The normal local repository boundary rejected that same-ticket reservation. Separately, an uncertain reservation for another ticket in the same repository did not prevent local approval or publication.

**Impact:** P3 crosses an explicit retained uncertainty barrier. Terminal-origin/process-death proof does not establish resource availability. The implementation's lease-file negative does not cover this valid reservation representation.

**Fix:** Apply custody-aware prepared-inventory admission under the existing repository exclusion for approval and every remaining publication/ref/link/queue write. Reject uncertain/active/preparing custody and the selected ticket's retained reservation; only permit unrelated preparations whose idle eligibility is actually established. Compose the existing opaque admission instead of reacquiring repository locks under TicketStore. Add both same-ticket and foreign-ticket reservation negatives, including fresh continuation, asserting no external effect and unchanged retained evidence.

### R2 — High: branch preconditions are rejected only after a real ref is created

**Evidence:** `packages/pa-core/src/documents/handoff-native-branch.ts:26–27,47–62` verifies the saved plan but initially checks the current link only by count/repository/name. `handoff-branch.ts:117–125` then authorizes and creates the ref. The lifecycle and exact planned-link checks run later in `tickets/handoff-intent.ts:65–68,105–106`, reached through `handoff-native-branch.ts:64–69` during materialization.

**Reproduced:** After publication, used the supported TicketStore writer to change the ticket to `implementing` / `builder/team-manager`. `complete-branch` returned `DOCUMENT_UNAVAILABLE`, but a new physical feature ref remained. A second probe removed/re-added the same planned branch with `linkedBy: foreign-owner`; it likewise created the ref before rejecting linkage. Neither probe edited source or forged registry evidence.

**Impact:** A known-invalid lifecycle or replaced native plan/link still causes an irreversible Git effect and leaves an avoidable partial operation. Publication-time and approval-time checks are insufficient for this later boundary.

**Fix:** Validate current lifecycle/assignment, exact original planned link, and relevant unsettled ticket intents under repository → ticket exclusion before starting/ref-creating an uncompleted branch operation, and recheck before each remaining external write. Keep completed-operation observation distinct so this does not break historical recovery or post-queue status. Tests must assert the ref/reflog and native effect history remain absent on pre-existing rejection.

### R3 — High: queue accepts a replaced materialized link that status rejects

**Evidence:** `packages/pa-core/src/documents/handoff-branch.ts:134–145` compares only repository/name/state/base/head/SHA. `handoff-native-branch.ts:54–62` returns a matching materialized link without validating its original attribution. `handoff-publication.ts:173–180` treats that result as sufficient for queue. In contrast, the new status verifier at `handoff-preflight.ts:168–169` explicitly rejects changed `linkedAt` / `linkedBy`.

**Reproduced:** Completed the original branch operation, then removed/re-added the materialized link through TicketStore as `foreign-owner`, preserving the physical ref and SHAs. Queue returned `queue: verified` and changed lifecycle/assignment. Immediately afterward, status reported both branch and queue as `conflict-or-unknown` because the original link attribution no longer matched.

**Impact:** The effect owner admits a link its independent verifier correctly rejects. Matching branch names/SHAs do not prove the unchanged native linkage required by P0, and the immediate success message overstates completion.

**Fix:** At the serialized branch/queue boundary, compare the full expected native link projection, including original `linkedAt` / `linkedBy`, against the exact saved plan/materialization result. Reuse that same invariant in effect admission and status. Do not adopt or repair replacement links. Cover replacement both before and after branch-journal completion, while retaining advanced-descendant reuse.

### R4 — Medium: revocation strands an already-applied queue after reply loss

**Evidence:** `packages/pa-core/src/documents/handoff-publication.ts:164–165` requires a currently usable queue grant before any same-operation observation. The actual ticket queue write precedes `completeEffect` at lines 178–180. Unlike publication's observation branch at lines 121–123, queue has no path to settle an already-applied original result after revocation.

**Reproduced:** Interrupted only the journal completion after the real queue write, verified `pending-implementation` / `builder/team-manager`, then finalized revocation. Replaying the original queue coordinates returned `DOCUMENT_AUTHORITY`; its original effect remained `started:true, completed:false`, and status stayed `partial`. That retained partial also blocks replacement reviews through `registry/handoff-reviews.ts:170–194`.

**Impact:** Revocation correctly fences missing effects but also makes an already-applied effect unresolvable through the available finite owner. The existing queue test recovers before revoking, so it misses this ordering. This is inherited consumer ordering newly exposed to v2, not a claim that retained v1 behavior regressed.

**Fix:** Provide v2 original-operation observational settlement before requiring a live grant: authenticate the current caller/custody, verify the original started operation and exact completed publication/ref/link/queue result, and settle only its native completion record. If any external write is missing, continue denying it after revocation. Preserve retained v1 API expectations and add the interruption → revoke → original-recovery test; do not require a replacement intent or another approval.
